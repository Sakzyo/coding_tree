## Issues

### Important

1. **A wake received during cancelled fresh-callback cleanup is discarded.** At `packages/core/src/session/run-coordinator.ts:126`, cleanup awaits `notify(entry.freshNotifications)` after checking `pendingWake` only at `:118`; it then unconditionally deletes the entry at `:129`. Reproduction: drain A starts asynchronous scope closure; tracked wake B enters the fresh bucket; `interrupt` clears `pendingWake` (`:183`); B's terminal callback pauses; wake C arrives during that callback. C sets `pendingWake`, but cleanup never checks it again. The focused probe observed `{"drains":1,"notices":[1,2,3],"active":0}`: C was notified without its newly requested drain running. In managed composition this can leave a newly admitted prompt pending after a post-stop submission while its admission reservation is already released. Detach the cancelled callback batch before awaiting it, give later registrations their own successor bucket, and re-evaluate scheduling after asynchronous notification before removing the entry. Add this exact deterministic regression; existing closure and interruption tests cover different interleavings (`packages/core/test/session-tracked-wake.test.ts:46`, `:161`).

2. **Known full-task acceptance gap: no authoritative legacy activation fence.** `packages/opencode/src/server/routes/instance/httpapi/server.ts:275` always binds `activation_unavailable` for a new root. The safe refusal is correct for this candidate, but first-release create/open activation is still unavailable. Implement the domain/legacy-owner fence and verify concurrent activation versus legacy admission/active execution before claiming full M2-06 or module completion. This finding does not request enabling execution or weakening the current refusal.
