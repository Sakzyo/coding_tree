## Approved contract and scope

`Configuration.Service.updateHardware({ root, expectedRevision, change, deviceCatalog })` is the one form/chat command. `change` is a full hardware replacement `{ hardware: readonly Hub[] }`; ingress is unknown for runtime validation. Existing persisted `Device`, `Hub`, and `Manifest` contracts remain unchanged. An existing manifest is required; an absent read returns `manifest_missing` at `['hardware']`, without initialization. Explicit initialization remains M6-01 `updateManifest`.

`DeviceCatalog = { sdkVersion, revision, hubs: [{ id, categories: [{ category, ports, types }] }] }` is the trusted producer's immutable selected-SDK plus project-hub rules snapshot. SDK and revision are exact nonempty producer identifiers, not discovered versions or a compiled-in support list. Local hub IDs identify project entries, not SDK hardware types. Catalog hub/category identities and port/type sets must be unique. A known hub with no matching category, category without a listed numbered port, or category without a listed device type fails deterministically. Each category port can be occupied once per hub; equal port numbers in distinct categories/hubs are allowed. Device names must be present and contain non-whitespace characters; uniqueness is exact and project-wide. Valid identifiers and names retain their bytes: no trimming, case folding, translation, or normalization.

The command validates/copies the replacement synchronously before I/O, reads through its own existing manifest owner, checks `expectedRevision`, then calls that owner's conditional update with `{ ...current.manifest, hardware }`. This preserves `managedPathing` and all current non-hardware fields. Invalid definitions do not reach a write; revision checks preserve observed external edits, including an edit during staging. The M6-01 final-check/publication race and filesystem limitations remain unchanged; this command does not provide filesystem CAS.

`HardwareError = { code, field: readonly (string | nonnegative integer)[] }` contains stable language-independent values. Codes: `invalid_hardware`, `invalid_catalog`, `manifest_missing`, `missing_name`, `duplicate_name`, `invalid_hub`, `duplicate_hub`, `invalid_category`, `invalid_port`, `occupied_port`, `invalid_type`. Domain failures identify the indexed field, e.g. `['hardware', 0, 'devices', 0, 'port']`; malformed structural hardware and catalog values use `['hardware']` / `['deviceCatalog']`. Negative/fractional ports are structurally invalid hardware; an integer absent from its catalog rule is `invalid_port`. Existing owner errors remain separate, including `invalid_manifest` for malformed expected revisions and `revision_conflict` with expected/actual revisions. Missing-name preflight handles omitted/empty/whitespace-only names before strict canonical decode. Core returns no translated prose.

**Authority limit:** M6-06 must derive and validate this catalog against the actual project's selected SDK and hub context. Model/form JSON must not select arbitrary rules as authority. This task neither discovers nor attests that producer binding. Tests use synthetic `fixture-sdk-*` / `fixture.*` catalog values; they make no actual SDK/device support or wiring claims. Definitions are project-side descriptions, not proof of physical connections. No Robot Controller configuration, Java mappings/proposals, SDK upgrades, or machine paths are written. Importing the module constructs no owner or I/O; owner resources are created inside the scoped Effect layer, with no bootstrap import.

## Review fix round 1 of 5 — capture the command envelope

Prior candidate: `e4d498ca0`. Independent review `M6-02-review.md` Important I1 confirmed that the wrapper retained validated/copied hardware but reread mutable `input.root` and `input.expectedRevision` after asynchronous `readManifest`. The owner already captures its own envelope, but receiving the wrapper's changed root can redirect publication to another project with identical manifest bytes; receiving a changed revision can substitute away a stale request.

Following systematic debugging and TDD, added two real-file regressions before changing production code. A read-port callback changes the command envelope's root from A to B while both projects have identical initial bytes. The correct result is hardware persisted only in A, with B's original bytes and directory contents unchanged. Another callback replaces the original stale expected revision with the newer revision after a real external edit; the correct result remains `revision_conflict` carrying the original expected revision and the observed current revision, preserving the external bytes. Both failed for the reported behavior before the fix (`fix1-red.log`: 2 fail, 0 pass, 19 filtered, 7 assertions). Neither test mocks the subject or owner.

The production fix captures `root` and `expectedRevision` into local scalar constants before validation or I/O, then uses only these values for initial read, comparison, conflict payload, and owner update. Hardware/catalog validation and discovery semantics are unchanged. No manifest adapter, Schema contract, foreign tests, Git/index, checklist, ledger, or root barrel changed. The admitted catalog/hardware were already validated/copied before the first read; the two new scalar captures close the remaining mutable-envelope gap.
