## Minimum recommended API and immutable bindings

Add `requestExercise` to the existing Location-scoped M12 service with `Effect.Effect<ExerciseResult, LearningError>`. Define its serializable command and result once in `packages/schema/src/ftc-learning.ts`, re-exporting exact canonical Schema values from Core. This Schema extension is required by shared contract conventions even though M12-03's task-local file list names only Core and its focused test.

The command retains the planned course/lesson IDs, canonical M6 `ManifestSnapshot` as `configuration`, and a minimal caller-supplied project applicability projection as `projectSnapshot`. That projection needs canonical local `projectID`, a concrete SDK version, and an explicit selected library/version binding when a pathing library is selected. These are trusted adapter facts, not model-discovered values. No public producer currently exposes that combined projection; define only M12's consumed boundary, not a duplicate M2/M6 project/configuration domain contract. The caller must bind project identity, configuration revision, SDK/library facts from the same observed project. M12 can validate shape and internal consistency; the manifest alone cannot prove project ownership.

The trusted course binding must pin the course version **for this immutable request**. Extend the existing injected course boundary narrowly to accept exercise applicability context, or add an exercise-specific binding method on that boundary while preserving old navigation callers. It may return metadata/values only; it may not resolve a sibling store itself. The lookup still uses canonical `ContentQuery`, with `localOnly: true` and the requested language. Minimum language extension: an explicit `language: en | zh` on the exercise command, consistent with the high-level M12 contract; do not use a global setting or silently fall back to English. The task's abbreviated signature omitted language, so this must be explicitly assigned in the implementation brief.

The exercise result needs the planned `kind`, course/lesson identity and exact lessonVersion, projectID, selected track, and requiredEvidence. Include `configurationRevision`, pinned courseVersion, SDK and selected library/version bindings so later M12-04 cannot reconstruct historical identity from current state. Requirements must retain each canonical exercise ID and supplied explanation/application/physical policy. A lesson allows multiple exercises; do not silently pick the first. The smallest lesson-level request can return all canonical `FtcKnowledge.Exercise` records as its `requiredEvidence`, preserving IDs, criteria and unspecified physical flags without introducing guessed evidence kinds. If callers instead need one exercise, explicitly add an exercise selector and bind its ID; that is a contract decision, not permission to discard other exercises.

The normal non-request result is `pathing_required` for a verified library-specific lesson when the managed selection is neither. Missing content/translation/local bytes, mismatched snapshots, malformed bindings, unsupported versions and absent lesson IDs should use existing typed errors and reasons where applicable (`course_unavailable`, `invalid_course`, `course_snapshot_changed`, `lesson_not_found`, `invalid_input`); they must not become successful requests or pathing-choice guidance. No result grants execution authorization or completion.

## Track classification decision before implementation

There is no explicit library-specific/autonomous marker on current `Lesson` or `Exercise`. Arbitrary `topic`, ID substrings, translated prose, and project `managedPathing` do not establish that a particular lesson needs pathing. `ContentRecord.library/libraryRange` can classify a wholly library-specific course, but cannot express a generic foundation lesson within a mixed course. It also cannot by itself supply verified lesson metadata when neither causes version filtering to return missing.

The coordinator must assign one explicit source-backed policy before dispatch:

1. Restrict M12-03 fixtures to separate generic and wholly library-specific courses, with a trusted course/lesson binding returning declared track requirement before applicability lookup; verify that declaration against matching M11 record metadata when content is found. Missing classification fails closed as unavailable, not as foundations. This needs only a narrow injected consumed contract, with production binding deferred to M11-07/08/M12-06.
2. If mixed courses are required now, assign the smallest canonical M11 lesson-level pathing requirement metadata extension, paired across translations and included in M11 validation/M12 snapshot-policy comparisons. M11 owns the declaration; M12 consumes it. No authoring of absent autonomous activities, entry policies, or capstones is implied.

Prefer option 1 for this isolated task unless an authoritative mixed-course producer contract is supplied. A generic lesson returns a generic/foundations track independently of whether the project selected Pedro or Road Runner. A declared Pedro/Road Runner lesson must match the managed selection and exact supplied library version; a different selected library yields incompatibility, never substitution or configuration changes. The public `track` vocabulary must explicitly represent foundations (for example `foundations | pedro | road-runner`); neither is a project choice, not an autonomous course track. Library display names remain supplied M11 bindings, not guessed translations of managed-choice literals.
