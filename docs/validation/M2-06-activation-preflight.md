# M2-06 authoritative legacy activation fence — read-only preflight

2026-10-07; after the I1 repair freeze. **Proposal only; no I2 implementation, registration, enabling, task/ledger change or runtime restart.** Current OpenCode new-root `activation_unavailable` and disabled managed execution remain intact. This is a software requirement before full M2-06/M1-11 first-release activation credit.

## Recommended contract decision

Use a small **legacy-domain, process-local root activity owner**, injected into M2 through a **scoped association boundary**. Count admission/setup, actual runner chains, queued work, background descendants and their cleanup. Atomically serialize new legacy acquisition and new-root association against that same owner. Refuse activation while any matching owner exists; never stop it automatically.

Prefer a callback-style `withAssociation(root, commit)` over separate `beginActivation/commit/release` commands. Holding the root exclusion through the actual association write makes rollback/cancellation ownership explicit and prevents callers from forgetting release. A prior `isIdle(root)` query, status-map scan or callback that returns before commit cannot provide this guarantee.

Two concrete choices need coordinator approval before coding:

1. **Recommended:** legacy owns the root arbiter in a new `packages/opencode/src/session/legacy-activity.ts`; M2 consumes only injected ports. A narrow default live layer shares this one owner through the existing process memo map, explicitly even when listeners have independent maps. Tests call a fresh scoped factory. No new loop, global service bus, private sibling store, import-time database/runtime construction or wire token.
2. **Alternative:** put the same pure root arbiter in Core Session domain so both host packages can name its service directly. This increases Core's legacy integration surface and still needs all lifetime producers below; it does not eliminate instrumentation or atomic association work. No need for this alternative is established by the current V2-only standalone/SDK host.

Recommend adding canonical association error `activation_busy` (retryable, no owner tokens) for known activity, retaining `activation_unavailable` for unknown/uncovered authority. Existing managed legacy requests remain `legacy_execution_disabled`; requests racing an activation may wait on its root exclusion and recheck durable association, or return existing `activation_unavailable`. There is no caller-supplied readiness flag.

## Why current placement/status cannot establish authority

- `SessionRunState`, `SessionStatus` and the legacy background wrapper are InstanceState-scoped, not process-wide root inventories. `SessionStatus.get` returns idle for an absent record (`session/status.ts:35–40`), and idle deletes its status entry. Neither proves absence of admission, detached title, task descendant, queued extension or asynchronous cleanup.
- InstanceState caches by current directory (`effect/instance-state.ts:30–61`). `InstanceStore.load` uses `FSUtil.resolve` (`project/instance-store.ts:108–110`); this canonicalizes existing paths but can preserve a missing path (`core/src/fs-util.ts:247–252`). Activation requires a verified accessible canonical existing root, using M2's existing realpath/stat/access identity, not host Project.ID (which may be global/shared), a copied manifest or caller header.
- The recorded Session directory determines the affected root. A descendant may reuse a Session by task ID, so its actual stored root must be resolved, not assumed from parent metadata. Parent and child roots each retain their proper claim if they differ.
- The current M2 `activation` adapter performs `activate` within folder resolution (`core/src/ftc/projects/adapters.ts:73–89`), while `FtcProjects.make.associate` calls `repository.associate` later (`core/src/ftc/projects.ts:283–296`). Replacing the unavailable callback with a successful idle check leaves an admission/association race.
- The ordinary OpenCode web handler and AppRuntime use the existing shared memo map (`httpapi/server.ts:112,328`; `effect/app-runtime.ts:50,111`). **Actual `Server.listen` uses a fresh memo map per listener** (`server/server.ts:125–127`). A node marked global in one graph is insufficient. The narrow activity owner must be explicitly shared across these graph instances, while test factories stay isolated.
- Standalone Server/SDK-next (`server/src/routes.ts:49–78`, `sdk-next/src/opencode.ts:12–27`) currently contain no legacy SessionPrompt graph. They still need tests proving the same public association boundary and disabled execution behavior. They must not imply that an independently hosted legacy owner in another process has been fenced.

## Minimal proposed public ports and state

Legacy domain exposes a scoped factory and a public service with runtime-only opaque leases:

```ts
acquire(root, verifyUnmanaged): Effect<Lease, ExecutionUnavailable>
retain(lease): Effect<Lease, ExecutionUnavailable>
release(lease): Effect<void>
withAssociation(root, commit): Effect<ProjectContext, AssociationError>
```

`root` is a captured canonical identity. `verifyUnmanaged` is a bound M2 read/check effect, not a boolean or wire function. It executes while the root exclusion is held, immediately before publishing the new activity claim. `commit` is the exact M2 association effect using the same canonical folder and its own repository. Root validation/membership remains M2-owned; legacy does not read M2 tables or Session tables directly.

Internal state is root-local exclusion plus exact held claim identities and closed/coverage state. Acquire/retain/release are interrupt-safe, idempotent for exact lease release, and cannot let an old callback release a newer claim. Retain requires a currently held parent lease and executes before child publication/fork. No durable owner record, replay token, per-Session service layer or generic registration bus. The service does not start work; existing Runner and BackgroundJob still own execution.

M2 should replace its current pre-resolution activation check with an association decorator that receives the canonical folder and encloses **check-existing + associate commit**. It can be supplied as a narrow `withAssociation` port to `FtcProjects.make` or a same-domain repository association adapter; prefer the latter if it preserves the existing public make signature and validation order. Pure folder identity stays separate. Existing associations remain readable/openable without claiming a new activation.

Atomic ordering:

1. Legacy acquire takes root exclusion, checks durable M2 association through its public bound port, publishes an activity claim before any admission/provider/tool/child work, then releases exclusion. A failed check creates no claim or work.
2. New-root association takes the same exclusion. Any live claim, accepted queue, detached child or cleanup claim yields typed busy; unknown coverage yields unavailable. No automatic interrupt.
3. If known idle, keep exclusion through the actual database association effect. A waiting legacy caller rechecks association afterward and fails closed. Failed/cancelled writes release exclusion; ambiguous outcomes are reconciled by the real repository, not a guessed in-memory managed flag.
4. A concurrent second open observes the committed association and reconciles the same identity. A root-specific reservation must not block a different canonical project.
5. Cancellation/shutdown stop accepting new claims and wait for exact registered owners to finalize before claiming idle. Dropped queued work releases only its exact never-started claim. No caller cancellation can imply a forked owner already ended.

The default live registry layer should build its **pure scoped factory through the existing shared process memo map**, even when the enclosing listener has a separate map; it must not store a listener-owned database connection. Operation-specific M2 check/commit ports borrow the caller's connection. AppRuntime, webHandler and actual listen must demonstrably receive the same owner object. Tests replace that live binding with fresh factories; no module-global test reset or import-time ManagedRuntime.

## Producer lifetime requirements

A public caller's outer `Effect.scoped` is insufficient because `Runner.startRun` forks into the persistent owner scope. Add a narrow optional runtime ownership hook to the existing Runner: acquire before a new run/shell/queued work item is accepted, transfer through shell-to-run handoff, and release after actual work plus finalizers. Joiners do not own/release the shared claim. Keep existing state machine, result fan-out and interruption semantics.

Likewise BackgroundJob needs a narrow acquire/terminal ownership hook inside its existing start/extend engine. Acquire before start publication; exact duplicate/no-start branches return unused reservations; queued extensions retain existing root ownership or hold an additional accepted claim; terminal release runs **after** scope closure, including the asynchronous close path. Its current `Scope.fork(..., "parallel")` means simply adding a resource finalizer to that same scope can release in parallel with child cleanup. A separate ownership scope or explicit post-close terminal callback is required. Reuse the existing job token to correlate internal cleanup; do not expose it as a project/drain identity.

The legacy wrapper and TaskTool bind these hooks using captured runtime root permits, not metadata. Before each title/summary/prune/result-notification fork, retain a child claim atomically; release only when the detached effect and its finalizers finish. Retain-to-fork failure and cancellation must release without publishing unowned work.

Command template expansion currently uses `Effect.promise(() => Promise.all(Process.text(...)))` without an abort signal (`prompt.ts:1419–1427`). The utility supports abort (`util/process.ts:57–106,111–170`), but cancelling the Effect currently need not await the underlying child process. The follow-on must either use the existing scoped child-process service and await cleanup, or explicitly keep the root claim until the outstanding process promise settles. Do not release the root claim merely because the waiting Effect was interrupted. This is an app-owned process lifetime fix, not proof that unrestricted Bash cannot launch external/detached OS descendants; M9 isolation remains a separate blocked requirement.

## Required deterministic test matrix

- Two independent Locations/windows using aliases of one canonical root share a process owner; another root can activate. Host Project IDs/global IDs and copied manifests cannot merge unrelated roots.
- Pause legacy admission before its first write and race activation: legacy wins => busy/no association; activation wins => legacy refusal/no admission/provider/tool. Cover prompt/noReply, direct loop, shell, command with template work, HTTP init and whole summarize/compaction.
- Pause the real repository commit: newly arriving legacy admission cannot slip through the old precheck gap. Fail/cancel commit; verify no leaked exclusion and retry reconciles actual durable outcome.
- Foreground runner busy, queued ShellThenRun, joined caller cancellation and asynchronous tool/process cleanup block activation until actual terminal cleanup; old callback cannot release a newer root claim.
- Foreground exits while detached title model, summary/prune, child task, accepted-but-not-started background extension or result injection remains: activation stays busy. Cancellation/promotion/status=completed before scope close does not establish idle.
- Block command-template subprocess cleanup; cancel caller; claim stays until actual child cleanup/promise settlement. Controlled local process only, no real tools/provider/network/robot.
- Same process: instantiate actual OpenCode webHandler, a fresh-map listener graph without opening a socket where possible, and direct AppRuntime domain entry. Prove shared owner identity and cross-graph exclusion. Test disposal of one graph while another retains active work; tests with distinct explicit factories remain independent.
- Existing managed roots always deny every legacy entrance; histories stay readable, no automatic interruption/replay/migration. Unknown ownership or missing canonical root remains typed unavailable.
- Standalone/SDK association behavior, generated Client and disabled managed raw/facade execution continue passing. First-release activation may only be credited after actual OpenCode host association succeeds when authoritatively idle and refuses concurrent legacy work.
- Preserve existing Session/Runner/BackgroundJob/TaskTool regression and package typecheck gates. Refresh scoped performance for changed ownership lifetimes; controlled ports do not establish production/platform acceptance.

## Limits and ruling needed

The proposed authority is **current-process app-owned legacy work**. It cannot discover independent legacy processes sharing the same root/database, arbitrary external terminal work, or escaped plugin/OS child processes. If first-release activation must cover those, coordinator must assign an explicit OS/process ownership mechanism or continue unavailable in that deployment mode. No status poll, directory scan or transport attachment establishes such authority.

Approve the owner placement, fence-through-commit port, typed known-busy outcome, actual graph sharing, generic Runner/BackgroundJob lifetime hooks and the exact path set before implementation. Keep `activation_unavailable` until producer coverage and atomic races are implemented and independently reviewed. Keep M9 production execution disabled afterward.
