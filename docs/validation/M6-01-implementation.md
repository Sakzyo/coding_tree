# M6-01 implementation evidence

Coordinator approved boundary before implementation: M6 owns a narrow atomic conditional adapter in `configuration/manifest.ts`, consuming public `FSUtil` filesystem methods. Shared `FileMutation` is unchanged. A staged complete file is renamed for replacement, or hard-linked exclusively for initialization. Expected bytes and canonical root/target are rechecked immediately before publication under instance-local serialization. External OS writers do not participate in this lock; there is an unavoidable final-check/rename race, and this is not filesystem CAS.

Contracts: recursively strict shared-only manifest; category/type are catalog identifiers whose relationship validation belongs to M6-02. `change` is a complete manifest, revisions are SHA256 of exact bytes, and `null` means explicit create-only initialization. Reads of absent manifests return an initialization proposal without writing. Events reflect observed updates/external changes without polling. No database authority, Java changes, robot configuration writes, or watcher registry.

Final approved port: `Pick<FSUtil.Interface, 'realPath' | 'readFile' | 'makeTempDirectory' | 'stat' | 'remove' | 'writeFile' | 'rename' | 'link'>`. The initial automatic scoped-directory cleanup was replaced after a real-filesystem regression showed it could delete a foreign directory through a moved/retargeted root. M6's `acquireRelease` finalizer checks both parent and staging device/inode, then canonical paths, before removing its own staging directory. A changed or unverifiable identity retains bounded orphan staging rather than deleting an unrelated path. Checks do not provide atomic no-follow removal or protection against a directory change after the final identity check. Missing platform inode identity also retains staging.

Final implementation sources are frozen. Worker owns no Git/index/checklist/ledger changes. Coordinator added the canonical `FtcConfiguration` root export, included in verification/hashes. No Protocol or HttpApi changes require generation.

## Cancellation investigation

The safe cleanup adapter initially exposed a pinned Effect cancellation-continuation surprise. Systematic debugging inspected `acquireRelease` acquisition/finalizer registration, FSUtil's public passthrough, Node shared `realPath` via Effect `effectify`, and callback/interrupt continuation handling. The isolated `finalizer-probe.ts` uses real temporary files, the same real public FSUtil service, and no M6 owner or global monkeypatches. In a cancelled parent, a direct cleanup generator received `true` from the filesystem-read chain; converting the preceding signal to void did not help, and a direct flatMap consumer was skipped. A fresh joined child received the actual canonical string, agreeing with native filesystem resolution. This locates the observed failure at cancelled-parent continuation handling; no specific upstream source defect is claimed.

Cleanup therefore runs in a joined uninterruptible child, isolated from the interrupted parent and fully awaited before releasing the update. It does not run a daemon or retain a universal directory registry. The final suite verifies cleanup with unchanged roots and safe preservation with retargeted/replaced roots. Cancellation before publication remains interruptible, including the final read/check; publication and its event are a short protected region.

## Scope and remaining gates

These are real local macOS filesystem tests with synthetic shared-manifest/catalog identifiers and controlled public-port races. They establish complete-file publication, create-only initialization, detected conflict preservation and scoped owner behavior. They do **not** prove a true filesystem compare-and-swap: noncooperating writers may still change a file between the last byte check and rename. Parent/staging identity checks likewise cannot make cleanup atomically no-follow. Ordinary cooperating calls serialize within the Location owner instance; hosts must share that owner for shared canonical roots. No polling or watcher registry was added.

Directory relocation can leave an owned staging directory behind; missing/inaccessible identity also retains it. The module deliberately avoids searching or deleting relocated/foreign directories. Broader untouched suites were not rerun per the dispatch scope; previously passing evidence remains coordinator-owned. Product application wiring, composed module acceptance, Windows filesystem/platform tests, actual SDK device-catalog relationships (M6-02), UI/i18n, Java/Gradle mapping proposals and all physical robot/release checks remain unrun/out of M6-01 scope. No such product support is credited by these isolated tests.

Final hashes are in `m6-01/source-sha256.log`; any later source change requires refreshed affected checks and hashes.
