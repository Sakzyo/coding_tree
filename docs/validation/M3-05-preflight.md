## Trusted authorization routes

`Tool.Context` supplies Session ID, selected agent, assistant message ID and tool call ID. Permission request source is exactly `{ type: "tool", messageID: context.assistantMessageID, callID: context.toolCallID }`. Leaf code captures `PermissionV2.Service` at construction and owns resolution, permission and side-effect ordering. Definition filtering is catalog visibility, not execution authorization. Permissions do not replace trusted project/Session membership, code policy, producer path enforcement, or M9 exact consent.

Use the M2 association `FtcProject.ProjectContext.projectID`; it is distinct from `location.project.id`. The caller resolver must verify project/root/Location and Session membership on each invocation, or expose a capability already enforcing those facts. Reject mismatches before invoking producer ports. Do not infer path authorization from a matching document project ID: the M3-04 review explicitly leaves document containment to M2/M5/host. Read-only inspection ports retain their protected-reader guarantees without giving the adapter filesystem access.

Source edits go exclusively through reviewed Agent policy. The asserted mode is checked against trusted policy. Direct mode permits only authorized requested application; plan-first returns the immutable actual plan. `approveCodePlan` and opaque edit authorization are never model tools or serializable output capabilities. User approval enters through the authenticated host route and binds plan/project/Session/proposal/revisions. Neither code mode grants deployment/start/tuning rights. Configure-generated Java/Gradle proposals must follow the same route before application.

Robot tools use the trusted agent route to M9, never a model-selectable `initiator: user`, approval event, approval token or mode change. Preparing an operation is not approval or execution. M9 owns action-specific parameters, capability evidence, physical identity/generation, artifact verification and later live pre-dispatch refresh. Existing controller `ProtocolEvidence` fixes identity to `unknown` and deployment to `unverified`; it cannot authorize a mutation. Generic shell/network/ADB/dashboard paths and production build subprocess access remain disabled until M9-08 proves mediation. A fixture preparation port has no dispatch capability.

## Honest structured output and sanitization

Return complete validated domain output, then project safe model-visible content; registry materialization alone owns generic bounding/retention. No adapter creates managed `outputPath`, truncates results a second time, or relabels captured log loss as complete output. Domain capture limits remain owner facts.

Use an explicit M3 tool-result union only for adapter categorization, composed from canonical producer records. The exact task requires `kind: build_failed` and no artifact on failure. Preserve distinct failure, cancelled, outdated and unknown states instead of collapsing them into success. The tool transport finishing successfully is different from a build succeeding. Expected invocation/authorization/domain errors may become a safe `ToolFailure` or a validated categorized domain failure; document that mapping consistently. Do not use `catchCause`: interruption and defects must survive. No automatic retry, old artifact substitution or fabricated positive result follows a failed port call.

| Domain fact | Projection requirement |
| --- | --- |
| Build/artifact | Keep owner-generated build ID, saved source/configuration revisions, actual exit/result and inputChanged. Failed/cancelled/outdated evidence cannot claim a current artifact. Optional artifact identity/digest comes from M5, never an M3 UUID or model success claim. |
| Code/configuration | Preserve independent buffer/disk revisions, dirty state, expected manifest revision and partial/conflict/unknown outcomes. InitializationProposal is proposed configuration, not observed hardware. Retain missing hardware facts and student Driver Station steps. |
| References | Keep captured SDK/library/version/language/localOnly query plus source URL, source version, digest, license, provenance and code identifiers. Missing/incompatible/not-local remain explicit; synthetic reference provenance does not become production evidence. |
| Diagnostics | Keep unknown logs/deployed-build association. A selected project does not establish observed project/build provenance. Later positive M10 results must retain live/stale/disconnected/missing, source/protocol/time/generation and valid zero. |
| Operations | Return M9 operation identity/status and actual error codes. An awaiting-approval request does not imply dispatch, success, stopping, or physical consent. |

No universal evidence ID exists in the current inspection/document/knowledge schemas. A content ID plus digest or source revision is provenance, not a newly minted successful action record. Preserve the identifiers the owner actually provides; leave unavailable evidence explicit. If the coordinator requires new owner-resolvable observation IDs, assign their schema and query to that owner rather than generating them in M3.

M3-04 supplies a trusted `Sanitizer` capability and explicit allowlisted projection pattern, not a production secret detector or general tool-output sanitizer. Tool output includes replacement text, document/conflict text, reference bodies, explanation text, log text, arbitrary IDs/paths and expected error details. Apply trusted sanitization to every arbitrary projected field before structured output, model content, registry retention or transcript persistence. Original revision/digest describes original owner bytes; label sanitized text as a projection. Preserve safe English/Chinese/API/device identifiers exactly; reject sensitive identifier rewrites safely. Do not expose credential stores, raw exceptions, extra producer properties or opaque authorization/caller objects.

Reuse the sanitizer interface and field-role conventions. Do not blindly invoke SystemContext loading wrappers for tool settlement: their unavailable/defect reduction is a context-specific contract, while tools must preserve interruption and defects under the Core Tool instructions. Translate expected sanitizer errors safely without embedding supplied causes. The host sanitizer implementation and end-to-end credential protection remain M3-06/M7 work; fixture redaction proves only tested capability behavior.
