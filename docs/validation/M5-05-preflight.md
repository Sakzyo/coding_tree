## Minimal service recommendation

Use one Location-scoped M5 build owner in the planned `java/build.ts`. Add the build facade deliberately without replacing the current document owner or requiring build ports to construct its existing document-only layer. Keep its state to an owner-local map of build IDs and immutable evidence plus scoped active children. There is no daemon, generic workflow registry, extra model loop, automatic retry/resume, tool discovery, setup call or sibling store import.

A minimal consumed-port boundary is:

1. **Trusted projects:** resolve the local association `projectID` to current `FtcProject.ProjectContext`. Reuse the existing project-port contract concept, not M2's implementation. Compare the full captured caller context with the authoritative context, including canonical root and Location placement. Caller JSON, a manifest, or a matching string is not authorization.
2. **Saved inputs:** acquire a scoped immutable saved-input lease for that authorized context and supplied descriptor. Return its project/root identity, complete saved-source identity, live configuration identity, and truthful unsaved-document basis. Retain an opaque runtime lease for execution/revalidation; never serialize it as a credential. The lease either names an immutable owned snapshot or supplies an authoritative change-aware interval check. The trusted port checks file/root scope at the actual read boundary. An arbitrary caller-provided hash or list is insufficient.
3. **Build process:** execute a fixed project-wrapper build recipe against that lease with the exact captured build JDK and Android SDK. It returns real ordered output and actual termination status through a scoped owned process handle. Its contract owns cancellation, descendants, pipes and cleanup. M5 decides the evidence status; the port cannot return an agent-provided `succeeded` flag. No arbitrary executable, shell command, Gradle task, environment map, init script or output-path selector comes from tool JSON.

For isolated tests these ports may use real temporary files and a small controlled process substitute. A separately labelled adapter test can launch a harmless test-owned executable if required to prove pipe/process ownership; this preflight does not need one. A fixture may legitimately authorize only its own temporary root and process. That fact cannot be promoted into authorization to execute a student's saved Gradle project. A production binding remains disabled until M9-08 proves the actual execution boundary, including project build scripts/plugins and indirect commands. Wrapper/PATH filtering, `--offline` and omission of ADB from the requested recipe are not that proof.

Capture immutable input copies before the first asynchronous boundary. Decode inputs/port records strictly, reject identity mismatches and refuse an incomplete saved-input scope. Use the canonical M4 descriptor directly; do not duplicate it or copy M5-03's evaluation-only local path configuration into the product. Wrapper bytes/properties are part of the saved-input basis; the process port must actually execute that wrapper, not global Gradle. JDK/SDK path strings and version labels alone do not establish unchanged executable/tool bytes; the trusted adapter must bind the tools actually consumed. This is future adapter evidence, not a new tool provisioner in M5-05.

The core flow should read: authorize project → capture saved-input lease → compare requested configuration revision → allocate owner build ID → run scoped process → finish output/termination capture → revalidate inputs and configuration → settle/store one immutable evidence result. Every error/cancellation path closes the acquired scope. An owner query by build ID returns the owner's record, with project authorization checked; it never decodes caller-supplied evidence as successful history.

## Saved identity and currency semantics

`sourceRevision` must identify **all saved inputs that the selected build consumes**, including files not open in the editor. A trusted snapshot adapter must cover Java/Kotlin or other existing build inputs, Android manifests/resources, root/subproject build files/settings, Gradle properties/version catalogs/locks, wrapper scripts/JAR/properties, `buildSrc`/included builds and local dependency inputs when relevant. Do not use only `*.java`, Git HEAD, timestamps, file sizes, the set of open documents, or sums of `diskRevision`. Do not hash secrets into public logs. Build-generated outputs/caches must not self-invalidate the input identity; include an existing generated input only when the selected build really consumes it as an input. The adapter owns that complete boundary, and rejects unsupported external inputs rather than silently ignoring them.

Recommendation for a byte-based source identity: one versioned canonical SHA-256 manifest of sorted project-relative input paths and exact-byte digests, covering file addition/deletion/rename, with a defined unambiguous encoding. Bind root identity separately. A manifest hash alone proves the recorded set, not that its producer found every relevant input or read it atomically. The adapter must establish completeness and consistent capture. This definition is a recommendation requiring coordinator adoption, not an existing source contract.

`configurationRevision` remains the producer's exact opaque nonempty revision, independently verified through the supplied live input port. Do not equate it to a source digest or invent a local M6 revision. Capture it before execution and revalidate it after execution even when no Java file changed. The build request's revision must equal the live captured revision; reject a stale request before launching. M5 imports no M6 implementation/store. Relevant saved configuration bytes also remain in the saved-input manifest when consumed by the build.

Two implementation choices permitted by the task must preserve the design's stronger interval condition:

- **Immutable snapshot:** the process receives only the retained, complete saved snapshot for its input basis. Query the live project's source/configuration after completion and retain an interval generation/change observation if every save/external edit must invalidate currency, including A→B→A. Endpoint equality alone establishes current byte equivalence, not absence of intervening saves. Established source/configuration changes mark evidence outdated. The snapshot's successful compilation remains historical evidence even if the live project changed.
- **Live saved project:** the trusted port establishes unchanged revisions throughout the start-to-settlement interval, with a monotonic generation or an equally strong change-aware guarantee as well as content identity. Comparing only endpoint hashes misses an A→B→A change and can mislabel mixed inputs as current. Ordinary watcher events without a completeness/race guarantee do not close that gap. If the interval cannot be established, no current success is issued.

For the smallest isolated service, keep snapshot/revision discovery inside the injected port rather than writing an ad hoc project crawler into the build owner. A test port must explicitly implement its promised semantics. Do not claim the real filesystem adapter exists merely because a fixture supplies a digest or generation.

An unsaved buffer is excluded from the process input. Retain its path and buffer/disk revision basis in evidence without copying its text into logs or implicitly saving/discarding it. The evidence may say that the **identified saved revision** compiled, but the presentation and consumers must not label the displayed dirty program as the current successful build. Buffer-only edits leave the saved source digest unchanged; they update the visible exclusion basis. Dirty state detected at settlement must remain visible even if the build started clean. M4 readiness continues to reject dirty context. M5-06 must reject dirty evidence as authorization for the current displayed program unless an independently authorized saved-artifact policy is explicitly adopted; this preflight does not introduce such a policy.

## Canonical evidence contract, once

There is currently no canonical `BuildEvidence`. The task plan gives a shape but omits Schema from M5-05's file list, while shared conventions require defining the contract in the first exposing task. **Recommendation:** explicitly assign a minimal addition to `packages/schema/src/ftc-java.ts` and focused Schema tests during M5-05; Core re-exports those exact values. Do not define an interim Core-only public `BuildEvidence`, reuse M4 `BuildVerification`, or create a second M5-06 identity. M5-06 later adds its canonical artifact contract and optional artifact association. This is a scope ruling for the coordinator, not a change made by this report.

Keep the plan's canonical members and define only the supporting semantics needed by this task:

| Member                  | Minimal meaning                                                                                                                                                                                        |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `buildID`               | M5-created ID with its own stable canonical schema/identifier; resolves through the owner query.                                                                                                       |
| `projectID`             | Local association ID, bound to the authorized canonical root retained in owner state.                                                                                                                  |
| `sourceRevision`        | Exact captured saved-input identity; never buffer revision or caller success data.                                                                                                                     |
| `configurationRevision` | Exact live producer revision used by this build.                                                                                                                                                       |
| `inputChanged`          | True only when source/configuration changes were established; an inability to verify is an error, not invented change.                                                                                 |
| `exitCode`              | Actual integer process exit status when observed; nullable/absent when no exit code exists. Cancellation, signal termination and spawn failure must not invent `0` or `-1`. Adopt one convention once. |
| `status`                | Closed `succeeded`, `failed`, `cancelled`, `outdated` set from the task.                                                                                                                               |
| `logs`                  | Retained actual ordered stdout/stderr entries; preserve stream identity and sequence. Bounded capture must expose any truncation. Service error detail is separate from process output.                |
| Saved-input basis       | Minimal additive `savedInputsOnly: true` and a truthful unsaved-document summary (project-relative path, document/buffer/disk identity where available); no buffer text.                               |
| Execution basis         | Exact captured canonical toolchain/selected fixed recipe available in the owner record; public host paths redacted where unnecessary. No new arbitrary command surface.                                |
| Failure detail          | Stable code for acquisition, start, stream, exit observation, revalidation or cleanup failure; not localized strings used as policy.                                                                   |
| `artifact?`             | Absent for M5-05. M5-06 is the producer of an artifact bound to this owner evidence.                                                                                                                   |

Define canonical request/result/error values with readonly records, stable domain-qualified identifiers, the existing `optional` helper and omission of undefined encoded properties. A request carries the planned project/toolchain/configuration inputs; runtime capabilities stay out of Schema. Do not add Protocol/Server/client generation or a root-barrel export merely for this isolated task. Follow package contract hygiene and exact facade/Schema identity tests.

Suggested terminal precedence, requiring coordinator adoption because the source does not specify the cross-product:

1. Settled cancellation remains `cancelled`, even when inputs changed, and retains actual partial logs/exit observation plus `inputChanged` if established. The owner stops/reaps its children; it does not overwrite the status with a later successful exit.
2. A completed process whose source/configuration changed is `outdated` (including a nonzero exit); preserve its actual exit/logs so both failed execution and obsolete basis are visible.
3. Unchanged inputs with observed exit `0`, complete output/termination capture and successful cleanup are `succeeded` for the saved basis. All other executions are `failed` with honest details and whatever exit/output was observed.
4. Failure to revalidate is `failed` with `input_verification_failed`; `inputChanged` stays false unless a change was positively established. Do not grant currency because revalidation was unavailable. Pre-admission malformed/unauthorized/stale requests fail with a typed domain error and launch nothing; no forged complete evidence is issued.

Effect interruption and explicit cancellation need one contract: a caller's interrupted fiber may not return `BuildEvidence`. The owner must nevertheless settle queryable `cancelled` evidence after cleanup, or expose a separate owner cancel/query handle. Do not simply catch interruption as success, detach an unowned child, or promise a synchronous cancelled return from an interrupted fiber. Owner disposal retires new admissions, cancels/joins its active builds and releases retained resources. Retention here is owner-local for its lifetime; durable cross-restart history is not silently added without a specified persistence requirement.
