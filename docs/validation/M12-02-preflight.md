## Public lookup and binding (no sibling-store access)

M11 already exposes `lookup(ContentQuery)` and `search({ query, text })` (`packages/core/src/ftc/knowledge.ts:33`–`:36`). `ContentQuery` requires explicit `sdkVersion`, `language`, and `localOnly`, with `library`/`libraryVersion` supplied together when used. Queries validate concrete SDK/library versions and filter applicability; no current-project store is read (`:44`–`:79`). Local availability never fetches content (`:81`–`:116`). `FtcKnowledgeContext.source` already calls the same public `lookup` (`knowledge/context.ts:8`–`:22`), so structured learning should use the returned document/lesson IDs, not a separate content namespace.

A current concrete query is `lookup({ id: 'foundations', sdkVersion: '11.1.0', language: 'zh', localOnly: true })`, demonstrated in `packages/core/test/ftc/ftc-knowledge/m11-04.test.ts:164`. Its SDK value is the supplied foundation pack binding, not a product default. For other courses the caller supplies the compatible SDK/library values explicitly.

Recommended port change: preserve the existing `LessonLookup.lessons` method for M12-01 callers and add one optional course-content lookup capability for the three new commands, accepting `{ courseID, language }` and returning a canonical validated `FtcKnowledge.ContentResult`. The supplied adapter closes over explicit applicability values and a chosen current content version. M12 imports only Schema contracts, never the M11 implementation/repository. Missing capability or metadata is a structured unavailable/domain error; old `recordAttempt`/attempt-only progress still works. Metadata-aware progress overlays navigation only after establishing current course/lesson identity. Do not perform two independent lookups and combine inconsistent versions: compare the course document's ordered lesson IDs/versions with the existing current-lesson snapshot before reading/writing navigation state; reject disagreement and request refresh.

`ContentQuery` has no exact content-version argument and lookup may return multiple applicable record versions (`knowledge.ts:57`–`:71`). The adapter must select exactly its explicitly pinned current record/document version and reject ambiguity or mismatch; it must not pick the first or newest record silently. Bind `courseID` to matching record/document ID and require record/document version/language agreement and locally available document bytes. `selectEntry`/`skipLesson` have no language parameter: use the supplied canonical en snapshot for policy; `nextLesson` loads the requested en/zh presentation of the same current binding. Bilingual policy equality is the producer invariant and must also be exercised by port fixtures. A language change never chooses another course/version or persistence key. Keep M11 missing reasons (`not_found`, `incompatible`, `missing_translation`, `not_local`) visible through the adapter/result instead of treating absence as end-of-course.

## Recommended minimum personal state (M12 owns)

1. Add canonical `EntryLevel`, command inputs, and `NextLessonRequest` with language `en | zh` to `packages/schema/src/ftc-learning.ts`. Add a canonical LessonResult that carries selected canonical Lesson, course ID/version, and requested language, plus explicit unavailable/no-next results. **No-next is a navigation outcome, never course completion.** Result tag names need coordinator selection because no existing LessonResult is defined.
2. Extend `LessonProgress.status` with `skipped` rather than introducing a parallel `state` field. A skip is a navigation preference; it does not create an Attempt or evidence and does not satisfy explanation, project application, physical validation, or any future prerequisite evaluation. Retain attempt IDs even on skipped material. If both attempts and an explicit skip exist, prefer `skipped` as the navigation status while retaining all original attempts unchanged.
3. Add optional current-course `courseVersion` and selected-entry metadata to Progress only when metadata-aware navigation is available. Keep the M12-01 attempt-only output unchanged when that optional capability is absent. Entry metadata needs only the exact level and bound course version; derive start ID/version from the current validated content instead of persisting a second mutable copy of content policy. Unselected entry defaults to the first supplied lesson for navigation without writing a fabricated selection.
4. Add two module-owned snake_case tables in `learning/sql.ts`: `ftc_learning_entry(course_id, course_version, entry_level)` with primary key `(course_id, course_version)`; `ftc_learning_skip(course_id, course_version, lesson_id, lesson_version)` with primary key over all four identity columns. Entry reselection updates only that course-version preference. Exact skip retries are idempotent. No project, language, profile/user, attempt, or sibling-ownership foreign key belongs in these tables. Caller-owned local-user DB isolation remains the existing mechanism.
5. Preserve old rows across upgrades. Current navigation consults only the exact current course/version and lesson/version; old skips or entry bindings cannot silently apply to updated content. Preserve all historical attempts and exact-retry behavior. New entry/skip writes validate lookup and policy before a transaction; failed/missing/invalid content writes nothing. Decode stored entry/skip records strictly with stable errors, as existing stored attempts are decoded. Do not overload failed/cancelled/unknown Attempt outcomes for skips.

`selectEntry` changes where navigation begins, not the state/evidence of preceding lessons. `skipLesson` requires an existing current lesson and explicit `skippable: true`; it records the current version internally because the planned command has no version parameter. Both return recomputed Progress. `nextLesson` is read-only and deterministic for an unchanged snapshot/state, preserving ordinary explanation/application requirements and known/unknown physical requirements in returned content. Selecting an advanced start must leave prior lesson requirements outstanding; it cannot manufacture completion of them. Do not add an exercise request, prerequisite graph evaluator, robot operation, or competence flag in this task.

## Decisions genuinely absent from the sources

These are concrete dispatch decisions, not reasons to reduce M12-02 requirements:

- **Production start/skip/physical policy:** neither requirements nor current foundation content states which lesson starts each entry level, which pages are skippable, or explicit physical requirements per exercise. The coordinator must approve M11-authored values (with a bilingual content/version/digest update), or authorize an isolated M12-02 contract implementation using supplied synthetic metadata while retaining production content enablement as a separate gate. Do not label the latter as production course entry/skip acceptance.
- **Meaning of `nextLesson` after recorded attempts:** M12-01 `recorded` means any submitted/failed/cancelled/unknown attempt, not success. Sources do not say that it advances navigation. Recommended conservative rule for M12-02: start at the selected entry point and return the first lesson not explicitly skipped; a recorded attempt alone does not exclude it. The coordinator should explicitly accept this rule or provide a navigation-only advancement rule that cannot award competence. Automatic completion is not an acceptable alternative.
- **Skipped page with physical exercises:** recommended interpretation is page navigation only, with all exercise requirements outstanding. A known physical requirement or unknown metadata cannot be treated as satisfied because the lesson was skipped. Whether the producer marks that page skippable is its explicit policy; M12 must preserve the requirement regardless. Do not invent physical evidence or silently declare physical lessons complete.
- **Version race in unversioned commands:** planned select/skip inputs contain no expected course/lesson version. The minimal implementation binds the snapshot it resolves during the call and returns that bound version. If the intended UI contract requires rejection of a stale viewed page, authorize optional expected-version inputs now; the source signatures do not already promise that protection. At minimum, mixed snapshots must fail rather than writing a skip for a different version.
