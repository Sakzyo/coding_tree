## Why acquire/revalidate cannot supply post-settlement currency as-is

inputs.acquire requires a Scope and creates a new immutable execution snapshot/recipe lease. Its revalidate/release promise complete interval observation for **that acquired lease**; release closes every lease resource. The owner deliberately drops it at settlement. The public contract does not promise that a new lease's generation uses the original lease's namespace, never resets, or records every relevant change since the original lease retired.

Reacquiring can produce today's source/configuration/dirty snapshot and can be cleaned up safely. It is still insufficient to prove original-build currency after A→B→A: equal endpoint identities plus a freshly reset generation may hide changes between leases. Keeping a closed revalidate closure working in this particular fixture is not a post-retirement production contract. Reacquisition also starts needless complete execution-snapshot allocation just to answer a current query.

Therefore assign **one explicit current query capability**, above, whose producer retains comparable monotonic change identity or equivalent trusted invalidation continuity from the original basis through query time. Its internal adapter may use reacquisition if it separately proves that continuity, exact recipe/tool/root binding and cleanup; no such proof exists in the frozen ports. A changed generation makes an old artifact permanently non-current for that basis even if bytes/configuration return to their prior values. Output/cache writes invalidate only when part of the declared actual input scope. Dirty initial/settlement build exclusions remain historical saved-basis limitations; clearing a buffer later cannot retroactively make it compiled. Current dirty exclusions also block current deployment validity. This is distinct from an arbitrary timer or polling policy.
