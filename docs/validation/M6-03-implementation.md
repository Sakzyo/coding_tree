## Inspection behavior and limits

Supported representative candidates are root `build.gradle`, `build.gradle.kts`, `build.dependencies.gradle`, `build.dependencies.gradle.kts`, TeamCode `build.gradle`/`build.gradle.kts`, Java files recursively beneath `TeamCode/src/main/java`, and `ftc-project.json`. Other project trees and applied external scripts are not followed. Clear top-level multiline `dependencies { ... }` blocks support single-line Groovy or Kotlin literal coordinate declarations using implementation/api/compileOnly/runtimeOnly/compile/testImplementation/androidTestImplementation. Comments and embedded string examples do not become coordinates/import evidence. Numeric-starting literal versions are reported as declaration evidence, not successful dependency resolution. Variables/interpolation/ranges/catalog references, conditional/nested blocks, inline blocks, multiline strings, custom loaders and code outside the supported declaration subset remain explicit `unsupported_gradle`/`dynamic_version` unknowns. This conservatively includes unparsed Gradle boilerplate and repositories; it may prevent conclusive `neither` even when no pathing dependency is present.

Java inspection recognizes line-starting ordinary/static imports after comment/literal masking; it is not a Java parser or a resolution oracle. It does not promise support for escaped Unicode imports, generated sources, alternative source sets, version catalogs, fully qualified usages or arbitrary Gradle syntax. Detected evidence is retained even when other inputs are incomplete; an absence is `unknown` when supported dependency inputs are incomplete. A missing manifest means no managed selection, not an inferred choice of neither. Both observed pathing libraries and a contradicting managed selection produce explicit conflicts without deletion, migration or compatibility claims.

SDK artifact names and coordinate/import examples reuse repository-owned pinned M5-03 evidence: FTC v11.1 commit `203c2d373765f0c66d121e3ec1cc3a18835f6534`, SDK 11.1.0, Pedro core/ftc 2.1.2 and Road Runner core 1.0.1, documented in `docs/validation/java-import.md`, `m5-03/checksum-verification.json`, and existing shadow result/provenance records. `m6-03/reference-evidence.md` retains pointers and source hashes. No new external package fact, download, install or compatibility assumption was required.

Requested root and port references are captured before asynchronous reads. Root aliases resolve once to canonical root, with device/inode and alias checks across later boundaries. External/internal source symlinks and symlink retargeting are rejected conservatively. File bytes are copied, hashed and read again to detect changed observations; changed sources have observed revision plus `state: changed` and do not supply parsed versions. Manifest bytes are hashed too; managed selection is admitted only when the public port snapshot revision matches the observed bytes and is captured before subsequent filesystem checks. These checks do not create an atomic project snapshot or eliminate every external filesystem check/open race. Future proposal/edit consumers must recheck current inputs.

Scope closure sets owner_closed, interrupts in-flight read fibers, and rejects escaped APIs. There is no source mutation, migration, proposal generation, process/Gradle/wrapper/Java execution, runtime server/app/provider/robot start, network or download operation. Actual filesystem tests bind only the infrastructure FSUtil adapter and use controlled public manifest ports, never sibling product fixtures. Windows and full host composition were not exercised; tests ran on available macOS arm64.
